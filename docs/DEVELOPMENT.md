# Development

Technical notes for maintaining (or reimplementing) Price Favorites.

> **Heads-up:** this mod hooks **undocumented internal GUI classes** of FS25.
> There is no official API for the prices page — everything here was discovered
> by runtime inspection. Expect game patches to occasionally break it, and see
> [What can break](#what-can-break-on-game-updates).

## Repository layout

```
modDesc.xml                 Mod descriptor: source file, input action, l10n, icon
modIcon.dds                 Shipped icon (256x256, DXT5) — generated by tools/make_icon.py
scripts/PriceFavorites.lua  The entire mod
tools/make_icon.py          Icon generator (Pillow); writes modIcon.dds + docs/icon.png
docs/                       Developer docs, icon preview, screenshots
```

The release zip contains **only** `modDesc.xml`, `modIcon.dds`, and `scripts/`.
`tools/`, `docs/`, `README.md`, and `.gitignore` are repo-only.

## The problem

The Prices view lives in the GUI frame **`InGameMenuStatisticsFrame`** (the
combined *Finances / Prices / Statistics / Vehicles / Hand Tools* page; its
prices sub-tab is the default one). The list of goods is driven by the frame
member:

```
self.fillTypes   -- array of sections; each section is an array of FillType objects
                 -- [1] = directly-harvestable crops, [2] = producible goods
```

Each entry is a real engine `FillType` object with `.name` (e.g. `"COTTON"`),
`.index`, `.title` (localized) and price fields. We identify a favorite by
`.name` and persist that.

We want a third section, **"Favoriten"**, pinned at the top, containing the
favorited goods — without removing them from their original section.

## How we do it — keeping the data layer and the table in sync

This was the hard part. The frame doesn't just render rows from `self.fillTypes`;
it also builds a **price-cell grid** (per visible row × selling stations) and runs
a per-frame `update()` that animates price fluctuations. **All of these derive
from `self.fillTypes` and must agree on the section/row counts.** Three things
matter:

1. **What we change:** we insert a favorites section at the front of
   `self.fillTypes`. The section holds **references to the same `FillType`
   objects** (not copies), so the game's own `populateCellForItemInSection`
   renders our rows exactly like the originals — correct prices, clickable — and
   the goods still appear in their original section.

2. **When we change it — critical.** The section must be present **at the moment
   the frame rebuilds its table**, so the rows, the price cells, and `update()`'s
   state are all built from the augmented data in one consistent pass. We hook:
   - `updateStationData` (**appended**) — runs right after the frame (re)builds
     `self.fillTypes`.
   - `rebuildTable` (**prepended**) — runs right before the frame builds the
     table cells.

   Both call `syncFavSection(frame)`, which removes any stale favorites section
   and rebuilds it from the current favorites set. Idempotent.

3. **Section titles.** `getTitleForSectionHeader(list, section)` is **index-based**
   (it does not read the section's contents). After we prepend a section, every
   following section's title is off by one, so our override returns the favorites
   title for section 1 and calls the original with `section - 1` for the rest.

### Approaches that did NOT work (and why)

- **Inserting at `reloadData` (too late).** The `SmoothListElement` rows updated,
  but `rebuildTable` had already built the price cells from the *original* two
  sections. `update()` then indexed a now-missing row → `attempt to index nil
  with 'index'` spam and corrupted add/remove. *Lesson: inject during the rebuild
  pipeline, not at row-render time.*
- **A "virtual" section via delegate wrapping** (return `n+1` sections, remap
  `getNumberOfItemsInSection` / `populateCellForItemInSection` / selection without
  touching `self.fillTypes`). This avoided the `update()` crash but caused a
  **re-entrant reload cascade**: the original `onListSelectionChanged` itself calls
  `reloadData`, and our remapped coordinates produced wrong fill-type/station
  lookups (`Missing filltype …`) plus heavy UI lag. *Lesson: don't fight the
  frame's selection→reload→populate coupling; let the original code run on real
  data.*

The working design is **real mutation, at the right time**.

## The toggle button & input

- An input action **`PRICEFAV_TOGGLE`** is declared in `modDesc.xml`
  (`<actions>` + `<inputBinding>`, default `KEY_f`) with an `<l10n>` entry for the
  controls menu.
- `getMenuButtonInfo` is **overwritten**. The frame returns
  `self.menuButtonInfo[subCategoryState]`; when that equals
  `self.menuButtonInfoPrices` / `…PricesWithHotspot` (i.e. the prices sub-tab is
  active), we append a button entry
  `{ inputAction = InputAction.PRICEFAV_TOGGLE, text = ..., callback = ... }`.
  `TabbedMenu:assignMenuButtonInfo` then registers the action event and shows the
  button (there are ≥5 button slots; prices uses 4, so the 5th is free).
- `onListSelectionChanged` is **appended** to remember the highlighted good
  (`frame.__pfSelected = self.fillTypes[section][index]`). Because we use real
  mutation, section/index map straight into `self.fillTypes` — no remapping.
- On toggle we flip the favorite, save, then `frame:rebuildTable()` +
  `rowList:reloadData()` to refresh, and nudge the list selection by ±1 section
  when adding the first / removing the last favorite (so the cursor stays on the
  same item).

## Persistence

Saved immediately on every toggle (not tied to the game save), per player:

```
<userProfileAppPath>/modSettings/FS25_PriceFavorites/favorites.xml
```

APIs: `getUserProfileAppPath()`, `fileExists()`, `createFolder()`,
`XMLFile.load/create`, `xmlFile:hasProperty/getString/setString/save/delete`.
Loaded once in `loadMap`.

## What can break on game updates

Ranked by likelihood/impact:

1. **`InGameMenuStatisticsFrame` internals.** It's undocumented. A renamed class,
   a renamed/removed method (`updateStationData`, `rebuildTable`,
   `getTitleForSectionHeader`, `getMenuButtonInfo`, `onListSelectionChanged`), or
   a changed `self.fillTypes` shape (e.g. no longer a 2-level section array, or a
   different member name) would break us. All hooks are guarded with
   `type(...) == "function"` checks and `pcall`, so the **mod should fail soft**
   (no favorites segment) rather than crash — but verify after each game patch.
2. **`self.fillTypes` section semantics.** We assume `fillTypes[s]` is an array of
   FillType objects and that the renderer reads it live. If GIANTS changes the
   number/meaning of sections or pre-flattens it, the segment or titles will be
   wrong.
3. **`getTitleForSectionHeader` being index-based.** If it becomes content-based,
   our `section - 1` shift would mislabel headers.
4. **Button-bar contract.** If `getMenuButtonInfo` stops returning
   `menuButtonInfoPrices`, or the menu runs out of button slots, the on-screen
   button disappears (the key binding still works).
5. **`SmoothListElement` selection API.** `setSelectedItem` /
   `selectedSectionIndex` are used only for the cursor-position nicety; if they
   change, worst case the cursor jumps on first-favorite again.
6. **`modDesc descVersion`.** Currently `97`; the test game reports `110`. Lower
   values still load (backward compatible), but bump it when convenient.

### Re-discovering internals after a breaking patch

The structure here was found by hooking generic GUI methods and dumping live
objects to `log.txt` (class via `ClassUtil.getClassObjectByObject`, members via
`pairs`, etc.). If a patch breaks the mod, a small throwaway probe that logs
`InGameMenuStatisticsFrame`'s methods and `self.fillTypes` is the fastest way
back in. Note that mods run in a **sandboxed Lua environment**, so `pairs(_G)`
does not enumerate game globals — reference them by name instead.

## Regenerating the icon

```
python tools/make_icon.py     # requires Pillow
```

Writes `modIcon.dds` (256×256 DXT5) to the repo root and `docs/icon.png`
(preview). Tweak the `top`/`bot` gradient colors, the star color, or the row
layout at the bottom of the script.

## Building the release zip

```
python tools/build.py        # writes FS25_PriceFavorites.zip to the repo root
```

The shipped zip must have `modDesc.xml` at its **root** and contain only the
runtime files:

```
modDesc.xml
modIcon.dds
scripts/PriceFavorites.lua
```

> ⚠️ **Use `tools/build.py`, not PowerShell `Compress-Archive`.** Compress-Archive
> writes ZIP entries with **backslash** separators (`scripts\PriceFavorites.lua`),
> which violates the ZIP spec; FS25 then can't resolve files in subfolders and
> fails with `Can't load resource ... scripts/PriceFavorites.lua`. Python's
> `zipfile` writes spec-compliant forward slashes.
